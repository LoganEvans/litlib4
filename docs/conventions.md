# Litlib4 Conventions & Workflows

## 1. File Structure & Headers
Every file generated by a human or AI **must** begin with the exact relative path as a comment on the very first line. This prevents drift during AI generation.
* Lean files: `-- FILENAME: path/to/file.lean`
* Markdown files: `<!-- FILENAME: docs/file.md -->`

## 2. Directory Strictness
* **`Signature.lean`**: May ONLY contain `Litlib.reference` blocks. No `def`s, `theorem`s, or proofs.
* **`Proofs/`**: May ONLY contain instances of the signature classes.
* **Textbooks**: Represented by a single folder (e.g., `Y1990/nakahara1990geometry/`). The `Signature.lean` file inside can contain dozens of `Litlib.reference` blocks for different chapters/equations.

## 3. Rigorous Signatures (Anti-BS Mechanics)
Litlib4 enforces strict mathematical boundaries to prevent physical theories from being proven via trivialities or logical explosions.
* **No Default Trapdoors:** Never use `:=` to provide a default body for a predicate in a signature class. Use `iff` constraints (`is_foo_iff : ∀ x, isFoo x ↔ ...`).
* **Enforce Non-Degeneracy:** Abstract variables like $F=0$ or $\det(g)=0$ routinely break physics theorems in Lean. Explicitly restrict domains (e.g., `Matrix.det g ≠ 0`).
* **Enforce Continuity/Integrability:** Abstract functions passed to derivatives or integrals must explicitly be bounded by Mathlib typeclasses like `Continuous`, `Differentiable`, or `MeasureTheory.MeasureSpace`.

## 4. Lean 4 Mathlib Style
* **Naming**: `UpperCamelCase` for Classes/Axioms. `camelCase` for variables and instance names.
* **Standardization**: Do not invent new mathematical structures. If a paper discusses "a continuous mapping between topological spaces," use Mathlib's `ContinuousMap` or `Continuous`. If it discusses an integral, use Mathlib's `MeasureTheory.integral`.

## 5. Git Flow & Pull Requests
Every commit and PR title MUST begin with one of the following category tags:
* `(sig)`: Adding or correcting a `Signature.lean` file. Reviewers must check the original PDF/Textbook.
* `(proof)`: Adding or updating a formalized proof in the `Proofs/` folder. Reviewers check Lean tactics.
* `(test)`: Adding/updating edge-case evaluations in a `Tests/` folder.
* `(tool)`: Modifying core macros (`Litlib/Core.lean`) or the `litlib_report.lean` tool.
* `(misc)`: Documentation, Nix environment updates, formatting.
