# Litlib4 Conventions & Workflows

## 1. File Structure & Headers
Every file generated by a human or AI **must** begin with the exact relative path as a comment on the very first line. This prevents drift during AI generation.
* Lean files: `-- FILENAME: path/to/file.lean`
* Markdown files: `<!-- FILENAME: docs/file.md -->`

## 2. Directory Strictness
* **Papers/Articles**: Represented by a single `Signature.lean` file inside the paper's directory (e.g., `Litlib/Y1975/belavin1975pseudoparticle/Signature.lean`).
* **Textbooks**: Because textbooks are massive, they MUST be chunked. Textbooks reside in a single parent folder, but contain multiple `.lean` files broken down by chapter or appendix (e.g., `Litlib/Y1984/wald1984generalrelativity/AppendixD/Conformal.lean` or `Chapter05/Dynamics.lean`). 
* **`Proofs/`**: May ONLY contain instances of the signature classes. No signature definitions.

## 3. Rigorous Signatures (Anti-BS Mechanics)
Litlib4 enforces strict mathematical boundaries to prevent physical theories from being proven via trivialities or logical explosions.
* **Explicit Tensor Indices**: Use `Fin N → Fin N → ℝ` instead of generic `Type*` for spacetime tensors.
* **Explicit Algebraic Expansions**: Do not use opaque functions to represent complex mathematical terms. Write out the full sums and products.
* **No Default Trapdoors:** Never use `:=` to provide a default body for a predicate in a signature class. Use `iff` constraints (`is_foo_iff : ∀ x, isFoo x ↔ ...`).
* **Enforce Non-Degeneracy:** Explicitly restrict domains (e.g., define inverses algebraically via Kronecker deltas).

## 4. Lean 4 Mathlib Style
* **Naming**: `UpperCamelCase` for Classes/Axioms. `camelCase` for variables and instance names.
* **Standardization**: Do not invent new mathematical structures. Use Mathlib's `Continuous`, `Differentiable`, `MeasureTheory.integral`, and `BigOperators` (`∑`).

## 5. Git Flow & Pull Requests
Every commit and PR title MUST begin with one of the following category tags:
* `(sig)`: Adding or correcting a signature file. Reviewers must check the original PDF/Textbook.
* `(proof)`: Adding or updating a formalized proof in the `Proofs/` folder. Reviewers check Lean tactics.
* `(test)`: Adding/updating edge-case evaluations in a `Tests/` folder.
* `(tool)`: Modifying core macros or reporting tools.
* `(misc)`: Documentation, Nix environment updates, formatting.
